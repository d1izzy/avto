# Vercel

Проект avto связан с приватным репозиторием d1izzy/avto и Vercel d1izzys-projects/avto.

Основной адрес: https://avto-d1izzys-projects.vercel.app/s/graphite
Кабинет: https://avto-d1izzys-projects.vercel.app/s/graphite/owner

- Build: npm run build
- Output: dist
- Переменные на этапе сборки: VITE_SUPABASE_URL, VITE_SUPABASE_PUBLISHABLE_KEY.
- SUPABASE_SERVICE_ROLE_KEY не добавляется во frontend.
- vercel.json содержит SPA fallback для прямого открытия вложенных страниц.
- После публикации проверьте создание и отмену тестовой заявки и вход владельца.
- Для E2E: E2E_SUPABASE_READY=1; для кабинета дополнительно E2E_OWNER_EMAIL и E2E_OWNER_PASSWORD. BASE_URL переключает тесты на опубликованный сайт.

PWA не кеширует Supabase REST: заявки всегда идут в сеть. Изображения кешируются на неделю.
Существующая удалённая база сохраняется при обновлении frontend. Demo seed повторно не запускается.

## Вход клиента по почте

Вход включён: почта → запрос ссылки в Supabase Auth → отдельный экран «Письмо отправлено» → переход по ссылке → возврат в исходное приложение → «Мой профиль». Ожидание и задержка отправки сохраняются в localStorage после закрытия окна. Обычная повторная отправка доступна через 60 секунд; при `over_email_send_rate_limit` новая попытка блокируется на час и объясняется возможность использовать уже полученное письмо. Это защитная пауза интерфейса, а не гарантия сброса общего серверного лимита. Отметка «Почта подтверждена» показывается после проверки пользователя в Auth, только при наличии `email_confirmed_at`.

Тестовое письмо на почту владельца отправлено 2026-10-03; владелец подтвердил получение. Это не доказывает доставку произвольным клиентам: без собственного SMTP Supabase допускает только почты участников организации и ограничивает отправку (сейчас 2 письма/час). UI показывает ошибку отправки и не сообщает об успехе при отказе сервера.

2026-10-03 исправлена URL Configuration проекта serviceslot: Site URL = `https://avto-d1izzys-projects.vercel.app`, разрешён точный redirect `https://avto-d1izzys-projects.vercel.app/s/graphite/account`. Настройки сохранены через панель Supabase. Контрольный запрос с заведомо недействительной ссылкой вернул HTTP 303 именно на опубликованный `/s/graphite/account` с ожидаемой ошибкой `otp_expired`, а не на localhost. После исправления Supabase принял отправку нового письма на разрешённую пользователем тестовую почту. Пользователь подтвердил успешный переход из нового письма: открылся профиль на основном сайте с отметкой «Почта подтверждена». Старые использованные ссылки повторно не действуют.

1. Подключить собственный SMTP в Authentication → Email → SMTP Settings проекта serviceslot. Стандартный отправитель Supabase не предназначен для писем произвольным клиентам.
2. В Authentication → URL Configuration установить Site URL и разрешить точный redirect `https://avto-d1izzys-projects.vercel.app/s/graphite/account`, а также `https://avto-d1izzys-projects.vercel.app/s/graphite/account?email_flow=*&sb_flow_id=*`. Оба сохранены в serviceslot. Для другого tenant/домена добавить отдельный путь; не разрешать произвольные внешние домены.
3. Оставить подтверждение почты включённым (`mailer_autoconfirm=false`). Новые ссылки используют PKCE и включённый в закреплённой версии supabase-js 2.117.2 экспериментальный `appendPkceFlowIdToRedirects`: разные попытки имеют разные verifier slots. При обновлении SDK перепроверить сценарий отказа повторной отправки. Старые implicit-ссылки ещё принимаются через `setSession`, пока действуют. Пароль клиент не задаёт.
4. Проверить письмо на внешнем клиентском адресе, переход по ссылке и появление сохранённой записи на втором устройстве. В автоматических тестах отправка и callback подменяются; они не заменяют эту проверку доставки.

Старый флаг `VITE_CUSTOMER_EMAIL_LOGIN_ENABLED` больше не используется. Профиль и сохранённые записи защищены существующими RLS и проверками принадлежности. Публичный вход не создаёт membership владельца студии.

Пароли SMTP и секретные ключи остаются на сервере Supabase; во frontend их не добавляют.

## Подтверждение из установленного приложения

Применена миграция `20261003115455_email_login_handoff.sql`. Приложение создаёт случайный 256-битный канал перед отправкой письма. Браузер, открывший письмо, передаёт в него только одноразовый PKCE authorization code и flow ID. Секретный verifier остаётся в исходном приложении; только Supabase Auth обменивает code + verifier на сессию. Проверка не основана на совпадении почты или флаге подтверждения пользователя.

В `email_auth_private.email_login_handoffs` нет почт, access/refresh tokens или verifiers. Прямые права на таблицу отозваны, RLS включён. Публичная функция — SECURITY INVOKER; закрытая реализация допускает pre-auth операции только по непредсказуемому каналу. Очистка после успешного обмена также требует `auth.uid()`. Канал живёт до часа, доставленный code — максимум 5 минут; продление и замена запрещены. Просроченные строки недоступны сразу, удаляются при следующем начале входа; успешные удаляются сразу, если запрос очистки дошёл. Создание ограничено 30 каналами в час по хешу адреса из gateway-заголовка; это дополнительный лимит, серверные ограничения Supabase Auth сохраняются.

Проверка подтверждения работает на всех публичных страницах, включая manifest start_url, раз в 4 секунды только при активном окне; продолжается при возвращении и восстановлении сети. В одном браузере вкладки сериализуют обмен через Web Locks. Сессия сохраняется стандартным Auth SDK. URL очищается, а политика `no-referrer` не передаёт параметры ссылки внешним изображениям. RLS профилей/записей и роли владельцев не менялись.

Автотесты моделируют отдельные хранилища PWA и браузера, проверяют сам PKCE challenge, закрытие/открытие приложения, старые ссылки, отказ повторной отправки, истечение и чужой code. Они не отправляют письма и не заменяют проверку на физическом iPhone. Для финальной проверки: запросить новое письмо именно из обновлённого приложения, открыть ссылку, вернуться в приложение в течение 5 минут и убедиться в появлении профиля. Старая ссылка, отправленная до обновления, не переносит вход между хранилищами.

`tests/sql/email-handoff.sql` проверяет реальную БД в транзакции с rollback: права, неизвестный канал, идемпотентную доставку, запрет замены, истечение и обязательность входа для очистки. Production-проверка redirect выполняется заведомо недействительной ссылкой без отправки писем.
